Compreensão do problema

Antes de escolher tecnologias, entenda a necessidade real.

Perguntas essenciais

  • Quem enfrenta o problema?
  • Em qual contexto ele ocorre?
  • Quais são as causas e consequências?
  • Como saberemos que a solução melhorou a situação?
  • Quais limitações de prazo, orçamento e equipe existem?
Exemplo: alunos perdem prazos porque atividades estão espalhadas entre e-mail, portal acadêmico e grupos de mensagens.

Enunciado recomendado

O público [tipo de usuário] enfrenta dificuldade para [atividade] porque [causa]. Isso provoca [consequência]. O projeto propõe [solução] para melhorar [resultado].

Exemplo preenchido: estudantes enfrentam dificuldade para organizar prazos porque as informações estão distribuídas. Isso provoca atrasos. O projeto propõe um painel unificado de tarefas acadêmicas.

Objetivos e escopo

Dentro do escopo: login, cadastro de tarefas, prioridades, alertas.

Fora do escopo: aplicativo nativo, IA recomendadora, integração com sistemas externos.

Dica: delimitar o escopo reduz retrabalho e crescimento descontrolado do projeto.

Requisitos e backlog

Transforme necessidades em itens claros, priorizados e testáveis.

História de usuário

Modelo: Como [usuário], quero [ação], para [benefício].

Como estudante, quero cadastrar uma atividade para acompanhar seu prazo de entrega.

Critérios de aceitação

  • Título obrigatório.
  • Data válida.
  • Associação a uma disciplina.
  • Confirmação após cadastro.
  • Exibição na lista.

Tipos de requisitos

Funcionais: descrevem o que o sistema faz.

Exemplo: permitir cadastro, edição e exclusão de tarefas.

Não funcionais: descrevem qualidade e restrições.

Exemplo: resposta em até 2 segundos; senhas criptografadas; interface responsiva.

4

Processo e colaboração

Organize o trabalho em ciclos curtos e transparentes.

Processo recomendado

  1. Planejamento da sprint.
  2. Reuniões rápidas de acompanhamento.
  3. Implementação e integração frequente.
  4. Revisão do incremento.
  5. Retrospectiva e plano de melhoria.

Papéis

Responsável pelo produto: prioriza e valida.

Facilitador: remove impedimentos e organiza o processo.

Equipe: projeta, implementa, testa, revisa e documenta.

Definition of Done

  • Código implementado e revisado.
  • Critérios atendidos.
  • Testes automatizados passando.
  • Pipeline aprovada.
  • Documentação atualizada.
  • Sem erros críticos conhecidos.

Exemplo de reunião diária

Ana: concluiu o formulário de login; hoje criará testes; impedimento: erro na configuração do banco.
5

Arquitetura e projeto

Escolha a solução mais simples capaz de atender ao problema.

Arquitetura simples

Para muitos projetos acadêmicos, um monólito modular é suficiente:

Frontend Web
    ↓
Backend / API
    ↓
Banco de Dados
    ↘
Serviços externos (e-mail, notificações)

Diagramas recomendados

  • Contexto: sistema, usuários e integrações.
  • Contêineres: frontend, backend e banco.
  • Componentes: módulos e responsabilidades.
  • Implantação: onde o sistema executa.

ADRs

Registre decisões importantes, alternativas e consequências.

ADR-001: usar PostgreSQL porque os dados possuem relacionamentos claros e exigem consistência.

Princípios de design

  • Alta coesão.
  • Baixo acoplamento.
  • Responsabilidades bem definidas.
  • Testabilidade.
  • Simplicidade antes de sofisticação.
Cuidado: não adote microsserviços apenas por moda. Eles aumentam a complexidade operacional.

7

Implementação

Desenvolva pequenas partes completas, testáveis e integráveis.

Boas práticas

  • Nomes claros e funções pequenas.
  • Evitar duplicação e código morto.
  • Validar entradas.
  • Tratar erros de forma segura.
  • Atualizar dependências.
  • Documentar decisões relevantes.

Configurações e segredos

DATABASE_URL=...
SECRET_KEY=...
API_TOKEN=...

Use .env localmente e publique apenas .env.example.

Implementação vertical

Entregue uma funcionalidade completa:

  • interface;
  • validação;
  • regra de negócio;
  • persistência;
  • testes;
  • documentação.

Tratamento de erros

Ao cadastrar uma tarefa com data inválida, o sistema deve rejeitar a entrada e mostrar uma mensagem clara, sem revelar detalhes internos.
8

Controle de versão com Git e GitHub

Integre trabalho, revisão e rastreabilidade.

Regras de ouro

  • Não trabalhar diretamente na branch principal.
  • Uma branch por tarefa.
  • Commits pequenos e claros.
  • Pull request antes do merge.
  • Revisão de código obrigatória.
  • Vincular PRs e commits às issues.

Convenção de commits

feat: adiciona cadastro de tarefas
fix: corrige validação da data
test: adiciona testes de login
docs: atualiza README
refactor: separa serviço de notificações

Fluxo sugerido

main
 ├── feature/cadastro-usuario
 ├── feature/listar-tarefas
 ├── fix/erro-login
 └── docs/readme

Checklist de pull request

  • Critérios atendidos.
  • Testes criados e passando.
  • Documentação atualizada.
  • Sem dados sensíveis.
  • Issue relacionada.

Testes e qualidade

Valide regras, integrações e fluxos completos.

Unitários

Validam funções ou classes isoladas.

Ex.: cálculo de prioridade e validação de datas.

Integração

Validam comunicação entre componentes.

Ex.: API + banco de dados.

Sistema

Validam o fluxo completo.

Ex.: login → cadastro de tarefa → listagem.

Teste de aceitação

Dado que o usuário está autenticado
Quando cadastrar uma atividade válida
Então a atividade deve ser armazenada
E deve aparecer na lista

TDD

  1. Escrever um teste.
  2. Observar a falha.
  3. Implementar o mínimo.
  4. Fazer o teste passar.
  5. Refatorar.
Cobertura ajuda, mas não substitui bons testes para regras críticas.

Integração contínua e entrega

Automatize validações sempre que o código mudar.

Pipeline mínima

  1. Checkout do código.
  2. Instalação de dependências.
  3. Lint e formatação.
  4. Testes.
  5. Cobertura.
  6. Build.
  7. Publicação do resultado.

Exemplo com GitHub Actions

name: CI
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
      - run: npm ci
      - run: npm run lint
      - run: npm test
      - run: npm run build

Manutenção, refatoração e evolução

O software continua mudando após a primeira entrega.

Tipos de manutenção

  • Corretiva: corrige defeitos.
  • Adaptativa: ajusta ao ambiente.
  • Evolutiva: adiciona funcionalidades.
  • Preventiva: reduz riscos futuros.

Dívida técnica

  • Código duplicado.
  • Testes ausentes.
  • Dependências antigas.
  • Documentação incompleta.
  • Configurações manuais.

Code smells

  • Funções grandes.
  • Classes com responsabilidades demais.
  • Nomes pouco claros.
  • Dependências circulares.
  • Mudanças espalhadas por muitos arquivos.
Refatorar: melhorar a estrutura interna sem alterar o comportamento externo. Ex.: extrair função, renomear variável, dividir classe ou remover duplicação.
